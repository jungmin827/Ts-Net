## QA 중 실 DB 에 들어간 테스트 데이터 (정리 필요)

접수 파이프라인을 복구·검증하면서 실제 `leads` 테이블에 **3건**이 들어갔다.

| 이름 | 번호 | 용도 |
|---|---|---|
| 테스트 | 010-1234-5678 | anon INSERT 복구 검증 |
| 검증 | 010-9999-8888 | 비평 에이전트의 재확인 |
| 김검증 | 010-2222-3333 | 레이트리밋 RPC 이관 후 검증 |

**이 행들은 지금 외부에 노출 중이다.** `live_feed` 뷰가 공개 anon 키로 읽히고,
5건 게이트가 Next 라우트에만 있었기 때문이다. 뷰 자체에 게이트를 심는 것은
`003_lock_down_functions` 다 — **그걸 적용하면 노출이 멈춘다.**
(재배열 전 번호인 005 로 적혀 있었다. 005 에는 `live_feed` 가 한 글자도 없다.)
그래도 행은 지워야 한다.

DB 쓰기 권한이 없어 이쪽에서 삭제하지 못했다. 어드민 상세에서 눈으로 확인한 뒤

## 자기 회귀 수정 — 2FA 강제가 만든 영구 잠금

C-11(2FA 실질 강제)을 고치면서 **더 나쁜 결함을 만들었다.** 기록해 둔다.

- **도입한 문제**: TOTP 미등록 계정을 로그인 직후 `signOut()` + 403 으로 끊었다.
  그런데 Supabase 는 TOTP 등록을 **로그인된 세션의 `mfa.enroll()` 로만** 제공한다.
  즉 등록할 방법이 사라져 계정이 영구 잠긴다. 어드민을 통째로 못 쓰게 만드는 변경이었다.
- **잘못된 전제**: "운영자가 Supabase 대시보드에서 TOTP 를 먼저 등록하면 된다"고 주석까지
  달았는데, 대시보드에는 최종 사용자용 TOTP 등록 UI 가 없다. 확인하지 않고 쓴 문장이었다.

**수정** — 가드를 두 단계로 가른다.

| 세션 상태 | 판정 | 이동 |
|---|---|---|
| TOTP 미등록 + aal1 | `ENROLL_REQUIRED` | `/admin/enroll-2fa` (유일하게 aal1 허용) |
| TOTP 등록 + aal1 | `MFA_REQUIRED` | 로그인 페이지의 코드 입력 |
| aal2 | 통과 | 요청한 화면 |

- `checkAdmin({ allowAal1: true })` 는 **등록 페이지 전용**이다. 다른 곳에 쓰면 2FA 가 무력화된다.
- 로그인 라우트는 미등록 시 **세션을 끊지 않고** `{ ok: true, enrollRequired: true }` 를 돌려준다.
- 등록 페이지는 진입 시 이전에 만들다 만 미검증 factor 를 정리한다 — 쌓이면 Supabase factor
  개수 상한에 걸리고 어느 것이 유효한지도 알 수 없게 된다.
- TOTP 비밀값은 브라우저 ↔ Supabase 사이에서만 오가며 우리 서버를 거치지 않는다.

**교훈**: 보안을 조이는 변경은 "그러면 정상 사용자는 어떻게 들어오는가"를 먼저 답해야 한다.
이번엔 답이 없는 상태로 조였고, 주석에는 확인하지 않은 우회 경로를 적었다.
