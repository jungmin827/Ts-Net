## F-01 [중간] 어드민 **목록**은 잘못된 날짜 하나로 통신사·상태·검색어까지 조용히 버린다

- **주장**: `docs/GOAL_EVIDENCE.md:90` — "입력 거부 | 기간 역전 · **달력에 없는 날**(2/29·2/31·13월) ·
  형식 오류 · 없는 프리셋 · 없는 통신사 **전부 거부**".
  `ad41b3a` 커밋 메시지도 "실측: 두 경우 모두 목록이 500 이 아니라 307(로그인 가드)로 정상 응답" 이라고 적는다.
- **실제**: 거부하는 것은 **내보내기 경로뿐**이다.
  `FE/lib/admin/filters.ts:107-113` 의 `parseLeadFilter` 는 검증에 실패하면
  `leadFilterSchema.parse({})` 로 **기본 필터를 새로 만들어 돌려준다.**

  ```
  parseLeadFilter({period:'custom', from:'2026-02-01', to:'2026-02-29',
                   carrier:'KT', status:'new', q:'홍길동'})
    → {"period":"30d","exported":"all","page":1}        ← 실측
    → resolvePeriod: 2026-09-09 ~ 2026-10-08
  parseExportFilter(같은 입력)
    → false / "달력에 없는 날짜입니다"                      ← 실측
  ```

  기간 역전(`from=2026-03-01&to=2026-01-01&carrier=SK`)도 같다 — 통신사까지 사라진다.
- **왜 문제인가**: 재현 입력은 `/admin/leads?period=custom&from=2026-02-01&to=2026-02-29&carrier=KT&q=홍길동`.

  화면에는 아무 메시지도 없다. 운영자는 "KT 홍길동 2월분" 을 물었는데
  "전 통신사 최근 30일 전체" 를 받는다. 해석된 구간 표기가 바뀌긴 하지만
  통신사·검색어가 빠진 것은 어디에도 드러나지 않는다.
  `ad41b3a` 가 "500 이 아니라 307" 만 확인한 것은 인증 때문에 화면을 못 봤기 때문인데,
  `parseLeadFilter` 는 **순수 함수라 DB 없이 바로 시험할 수 있었다.**
  `verify-export.mjs` 가 `parseExportFilter` 만 돌리는 것이 이 구멍을 그대로 남겼다.
- **조치**:
  ① `FE/lib/admin/filters.ts` — `leadFilterSchema.superRefine(rangeOrdered)` 를
     `exportFilterSchema` 처럼 **모듈 상수로 올려** 두 경로가 같은 스키마를 쓰게 한다
     (지금은 `parseLeadFilter` 안에서 매 호출 새로 조립하고 있어 둘이 갈라졌다).
  ② 실패 시 전부 버리지 말고 **문제가 된 키만** 떨어뜨린 뒤 재검증하고,

  ③ `FE/app/(admin)/admin/leads/page.tsx` 가 `dropped` 를 받아
     `LeadFilterBar` 위에 "입력이 올바르지 않아 ○○ 조건을 적용하지 못했습니다" 를 띄운다.
  ④ `FE/scripts/verify-export.mjs` 의 `[입력 검증]` 블록에 `parseLeadFilter` 도 돌려

## F-02 [중간] 히어로만 거터가 12px — 모바일 전 구간에서 좌측 정렬선이 4px 어긋난다

  (300 + 32 + 4 = 336 ≤ 336, 360px 에 들어맞는다)".

  `Footer.tsx:68`, `[carrier]/page.tsx:93` …

  360px 뷰포트 실측(`getBoundingClientRect`):

  | 요소 | left | right |

  | 헤더 로고 `<a>` | **16.0** | 84.7 |
  | 히어로 `<h1>` | **12.0** | 348.0 |
  | 히어로 폼 카드 | **12.0** | 348.0 |

  튀어나온 채 나머지가 줄을 맞춘다. 수직 정렬선은 1px 어긋남도 보이는 축이다.

  `360 − 32 − 24 − 4 = 300` 으로 **정확히 같은 결과**가 나온다.

- **조치**: `FE/components/sections/Hero.tsx:144` 를 `px-4` 로 되돌리고,
  `:234` 의 카드 패딩을 `p-4 sm:p-6 md:p-7` → `p-3 sm:p-6 md:p-7` 로 내린다.
  `min-w-0`(`:146` `:233`)과 `LeadForm.tsx:229` 의 스크롤 래퍼는 그대로 둔다 —
  그 둘은 안전장치라 유지하는 편이 맞다.

## F-03 [높음] 통신사 상세의 하단 상담폼 Turnstile 이 360px 에서 22~26px 잘린다

- **주장**: `docs/UI_PORT_LOG.md` — "재측정 320/360/390px 넘침 0 · 페이지 가로 스크롤 없음.

  `GOAL_EVIDENCE.md` 판정표도 "반응형 | 320·360·390px 넘침 0 | 동급" 으로 적는다.

  `FE/components/forms/LeadForm.tsx:229` 의 `overflow-x-auto` 안쪽을 재면 —

  | 경로 | 뷰포트 | 래퍼 clientWidth | 위젯 scrollWidth | 잘림 |
  |---|---|---|---|---|
  | `/` | 360 | 300 | 300 | **0** ✓ (히어로는 고쳐졌다) |
  | `/` | 320 | 260 | 300 | 40px |
  | `/kt` | **360** | **274~278** | **300** | **22~26px** |
  | `/kt` | 320 | 238 | 300 | 62px |

  `max-w-xl px-4` + 카드 `p-6`: `360 − 32 − 48 − 2 = 278 < 300`.
  히어로만 고쳤고, 통신사 4페이지의 **본 접수 폼**은 손대지 않았다.

  체크박스는 왼쪽이라 **제출 자체는 된다** — 그래서 더 나쁘다. 아무도 실패로
  보고하지 않는데, DB수집의 마지막 칸에 가로 스크롤바가 생기고
  Cloudflare 브랜딩·Privacy/Terms 링크가 잘린다.
  그리고 방법론 문제가 하나 더 있다 — **줄지 않는 유일한 요소를
  `overflow-x-auto` 로 감싼 순간 "페이지 넘침 0" 은 구조적으로 항상 참이 되어
  증거이기를 그만둔다.** 재검 지표가 자기 수정에 의해 무력화된 것을 못 봤다.

     바꾸거나, 지금의 칸 안 스크롤을 **의도된 동작으로 문서에 남긴다.**
  ③ `docs/UI_PORT_LOG.md` 재검 표에 "페이지 넘침" 말고
     **"스크롤 래퍼 안쪽 잘림(px)"** 열을 추가한다. 지금 지표로는 영원히 0 이다.

## F-04 [높음] `.cta-fill` 색면이 흰 배경 대비 2.56~2.88:1 — 이 프로젝트가 요금 막대에 적용한 기준에 미달

- **주장**: `CLAUDE.md:28` — "| `.cta-fill` | 주 전환 버튼 — `#08bb45 → #07b040` + 진한 글자 | **6.88 / 6.12** ✓ |".
  바로 아래 `:36-37` 은 "⚠ **요금 막대는 비문자 요소라 3:1(SC 1.4.11)을 따로 따진다** —
  `--brand` 는 흰 배경 대비 2.88 로 **미달**이므로 막대에는 `--brand-dark` 를 쓴다" 라고 못 박는다.
- **실제**: 6.88 / 6.12 는 **글자 대비**다. 같은 면의 **경계 대비**는 재지 않았다.

  ```
  #08bb45 (cta-from) vs #ffffff = 2.56:1
  #07b040 (cta-to)   vs #ffffff = 2.88:1
  --shadow-cta = 0 4px 14px -3px rgb(5 144 58 / .45)   ← 흐린 글로우, 경계선이 아니다
  ```

  `FE/app/globals.css:241-244` 의 `.cta-fill` 에는 `border` 가 없고,
  9개 사용처 중 `PlanCards.tsx:105` · `PlanCalculator.tsx:223` ·
  `(site)/layout.tsx:52` 는 `shadow-cta` 조차 없다(실측 `box-shadow: none`).
  즉 흰 면 위의 초록 사각형이 **자기 색 말고는 자신을 알릴 수단이 없는데**
  그 색이 2.56:1 이다.
- **왜 문제인가**: 재현은 `/kt` 의 추천 카드 "이 상품 상담하기" 버튼
  (실측 308×55, `background-image: linear-gradient(rgb(8,187,69), rgb(7,176,64))`,
  `box-shadow: none`, 부모 배경 `rgb(255,255,255)`).
  저시력·흑백 인쇄·햇빛 아래 화면에서 버튼이 바탕에 녹는다.
  규범 해석에 다툼의 여지는 있다 — 글자 라벨이 컨트롤을 식별한다고 보면
  1.4.11 대상이 아니라는 읽기도 있다. 그러나 **이 프로젝트는 이미 반대 해석을
  택해 요금 막대의 색을 바꿨다.** 같은 문서 안에서 막대에는 3:1 을 요구하고
  사이트 전체의 주 CTA 에는 면제하는 것은 기준이 아니라 편의다.
  `7d33c72` 가 흰 글자 전제를 뒤집으면서 글자 대비만 다시 쟀고,
  그 과정에서 면이 밝아진 쪽(4.77/6.02 → 2.56/2.88)은 아무도 재지 않았다.
- **조치**: 쨍한 면을 지키면서 경계만 세운다 —
  `FE/app/globals.css:241` 의 `.cta-fill` 에
  `box-shadow: inset 0 0 0 1px var(--brand-dark);` 를 더한다
  (`#0a8230` vs 흰 배경 4.94:1 ≥ 3). 그라디언트 두 끝은 그대로 둔다.
  `CLAUDE.md:28` 표의 `.cta-fill` 행에 **글자 6.88/6.12 · 경계 2.56/2.88(+테두리 4.94)**
  를 나눠 적어, 다음 사람이 두 축을 같이 보게 한다.

## F-10 [낮음] 왕복 검사와 `kstRangeToUtc` 의 연도 해석이 서로 다르다

- **주장**: `FE/lib/admin/filters.ts:34` — "문자열 → 날짜 → 문자열 왕복이
  **같은 값으로 돌아오는지**까지 본다."
- **실제**: 왕복은 `new Date("YYYY-MM-DDT00:00:00Z")`(ISO 연도 리터럴)로 보는데,
  정작 값을 쓰는 `FE/lib/kst.ts:49-51` 은 `Date.UTC(y, m-1, d)` 다.
  `Date.UTC` 는 **연도 0~99 를 1900~1999 로 옮긴다.** 두 함수가 같은 문자열을
  다른 날로 읽는다.

  ```
  parseExportFilter({period:'custom', from:'0026-01-01', to:'0026-12-31'})
    → success                                            ← 실측
    → kstRangeToUtc: 1925-12-31T15:00Z ~ 1926-12-31T14:59:59Z
  '0000-01-01' ~ '0099-12-31'
    → 1899-12-31T15:00Z ~ 1999-12-31T14:59:59Z
  ```
- **왜 문제인가**: 재현은 `/api/admin/export?period=custom&from=0026-01-01&to=0026-12-31`.
  충돌은 아니고 결과는 0건이라 피해는 작다. 문제는 **검사가 지키겠다고 선언한
  불변식("문자열이 가리키는 날과 실제 조회되는 날이 같다")을 지키지 못한다**는 점이고,
  `verify-export.mjs` 의 기간 쿼리 케이스가 전부 2026년이라 영원히 안 걸린다.
- **조치**: `filters.ts` 의 `dateString.refine` 을 `kstRangeToUtc` 와 **같은 해석**으로 맞춘다 —
  `const [y,m,d] = v.split("-").map(Number); const dt = new Date(Date.UTC(y, m-1, d));`
  로 왕복시키고, 동시에 `y >= 2000 && y <= 2100` 같은 현실 범위를 건다
  (`leads.created_at` 이 들어올 수 있는 구간 밖은 애초에 입력이 아니다).
  `verify-export.mjs` 에 `0026-01-01` 과 `9999-12-31` 을 케이스로 추가한다.
