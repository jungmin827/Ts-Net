### 어드민 — 화면이 아니라 감사로그로 확인

로그인부터 목록·필터까지 수동으로 눌렀고, 그 흔적이 `access_logs` 에 남았다.
지금까지는 서버 로그에 `access_logs 기록 실패: SUPABASE_SERVICE_ROLE_KEY가
설정되지 않았습니다` 가 찍히고 있었다 — **감사 기록이 통째로 유실되는 상태**였다.
키를 넣은 뒤 끊김 없이 들어온다.

```
  7  LOGIN  admin            2026-10-13 14:09 KST
  8  LIST   leads:dashboard  rows=3
  9  LIST   leads            rows=3
 12  LIST   leads            rows=0   (period=month, status=INSTALLED)
 13  LIST   leads            rows=3
```

`row_count` 가 실제 행 수(3)와 맞고, `status=INSTALLED` 필터가 0건을 반환한 것도
맞다 — QA 3건은 전부 `NEW` 다. 목록은 `phone_masked`(`010-****-5678`)만 받는다.

**단서 둘:**

- `DECRYPT` 기록이 0건이다 → 상세조회의 전화번호 복호화 버튼은 아직 안 눌렸다.
  규칙 3 의 "복호화 시 `access_logs` 기록" 경로는 **코드 검증만** 되어 있다.
- `EXPORT` 기록이 0건이다 → **목표 3 의 엑셀 내보내기를 사람이 눌러 본 적이 없다.**
  `verify-export.mjs` 는 통과하지만 그건 스크립트다. 실제 `.xlsx` 를 받아 열어
  보는 것이 남았다.

### 새로 드러난 것 — 파기 함수에 호출자가 없다

`pg_cron` 이 설치돼 있지 않다 (`cron.job` relation does not exist, 확장 목록에
`pgcrypto` 뿐). `purge_expired_leads()` · `purge_old_access_logs()` 는 존재하고
익명 호출도 막혀 있지만, **아무도 주기적으로 부르지 않는다.** 보존기간이 지난
개인정보가 스스로 지워지지 않는다는 뜻이다 — 함수가 있다는 것과 파기가 일어난다는
것은 다르다. `BE/README.md` 5번(대시보드에서 pg_cron 활성화 + 스케줄 등록)이
이 항목이고, 체크박스가 비어 있던 이유를 이제 근거로 적을 수 있다.

   아닌 **아무 일도 일어나지 않는다.** `ConsultSection` 으로 빼서 페이지와

2. **`Reviews.tsx` 의 `/review` 링크**는 후기가 1건이라도 생기는 순간 404 를

   터지는 종류다. 검사 G0 가 "코드가 거는 내부 링크 ⊆ 존재하는 라우트" 를
   데이터 상태와 무관하게 본다.

### 후기를 쓸 수 있는 사람이 운영자뿐이었다

`reviews` 에 anon INSERT 정책도, 작성 API 도, 폼도 없었다. 어드민은 단일
계정 1개(운영자)다. 즉 `/review` 에 "가입 후기" 로 뜰 수 있는 글은 **전부
운영자가 쓴 글**이었다 — 소비자가 제3자 경험으로 읽는 자리에 사업자의 자기
서술이 들어가면 표시광고법상 거짓·과장 광고 소지가 있다.

CLAUDE.md 규칙 1 이 `leads` 를 두고 막으려던 것과 같은 종류라, 규칙 1 에
그 문장을 넣었다. 분석·선택지 비교는 `docs/REVIEW_AUTHORSHIP.md`.

제출 경로(`/review/write` → `/api/reviews`) + 승인 화면(`/admin/reviews`)을
만들었다. 승인 전 글이 안 새는 보장은 애플리케이션이 아니라 **RLS** 에 있다
(마이그레이션 008): anon INSERT 는 `is_published = false` · `view_count = 0` ·
`admin_reply is null` 인 행만 통과하고, anon 에게 UPDATE·DELETE 를 주지 않는다.

이름·연락처·비밀번호·이미지를 **받지 않는다**(다모아와 같은 선택). 받지
않으면 마스킹할 것도 유출될 것도 없고, **개인정보 동의를 받을 대상도 없다.**

### 어드민 검색어가 정리 없이 필터 DSL 에 들어가고 있었다

`lib/admin/leads.ts` 가 `query.or(\`name.ilike.*${filter.q}*,…\`)` 로
검색어를 그대로 끼워 넣었다. `.or()` 는 PostgREST 가 문자열을 파싱하는 필터
DSL 이라 `,` 는 조건을 하나 더 만들고 `.` 은 `열.연산자.값` 으로 읽혀 다른
열을 가리킨다. 어드민은 이미 인증된 주체라 새로 열리는 노출은 없지만,
**이름에 쉼표나 점이 들어간 검색이 조용히 엉뚱한 결과를 낸다** — 상담사에게
넘길 명단이 한 건 모자라도 아무도 모르는 종류의 고장이다.

정리 규칙을 `lib/postgrest.ts` 한 곳에 두고 브랜드 타입(`SafeLikeTerm`)으로
바꿨다 — 정리를 거치지 않은 문자열은 컴파일이 거부한다
(`getReviewPage({ q: "x,phone_enc.ilike.*" })` → `TS2322` 확인).

### SEO 기반이 하나도 없었다

`/sitemap.xml` `/robots.txt` 둘 다 404, `metadataBase` 는 TODO.
정본 주소를 `NEXT_PUBLIC_SITE_URL` 하나가 결정한다(`lib/site-url.ts`).
비어 있거나 **운영 빌드에서 로컬 주소**면 robots 가 전체 수집을 막고
sitemap 을 비운다 — 틀린 canonical 은 없는 canonical 보다 나쁘다.
(`.env.local` 에 `http://localhost:3000` 이 들어 있었다.)

검색·2페이지 이후 목록은 `noindex, follow` + canonical 을 목록 첫 페이지로.
