# 후기는 누가 쓸 수 있는가 — 구조가 답을 이미 정해 두고 있었다

작성 2026-10-08. 게시판을 만든 뒤 작성 경로를 확인하다 발견.

## 발견

`/review` 는 `reviews` 테이블을 읽어 "가입 후기" 로 보여준다. 그런데
**방문자가 후기를 남길 경로가 없다.**

| 확인 | 결과 |
|---|---|
| `reviews` 에 anon INSERT 정책 | **없음** (`001_init_schema.sql` 262~271행 — select 만 `anon`) |
| 후기 작성 API 라우트 | **없음** (`FE/app/api/` 에 `reviews` 없음) |
| 후기 작성 폼 | **없음** |
| 쓰기 권한 | `reviews_admin_write` — `is_admin()` 만 |

즉 **화면에 뜰 수 있는 후기는 전부 어드민이 직접 넣은 글이다.**
어드민은 단일 계정 1개(운영자)뿐이므로, 그 글의 작성자는 운영자다.

## 왜 문제인가

운영자가 쓴 글을 "가입 후기" 라는 이름으로 내보내면 **표시·광고의 공정화에
관한 법률** 상 거짓·과장 광고에 해당할 소지가 있다. 소비자가 제3자의 경험으로
읽도록 배치했는데 실제로는 사업자의 자기 서술이기 때문이다.

CLAUDE.md 규칙 1 이 막으려던 것과 **정확히 같은 종류**다:

> 실시간 신청현황은 실제 `leads` 데이터만 마스킹해서 노출한다.
> 가짜 접수 데이터를 생성·시딩하는 코드를 짜지 않는다. 표시광고법 위반 소지.

그 규칙은 `leads` 만 이름으로 적고 있다. 그래서 `reviews` 는 규칙의 글자
밖에 있었지만, **규칙이 보호하려는 것의 안쪽에 있다.** 스키마의
`is_published boolean default false` 와 주석 `-- 승인 후 노출` 은 원래
"누군가 제출하고 → 운영자가 승인한다" 를 전제한 설계다. 제출하는 쪽이
빠진 채로 승인 단계만 남아서, 승인이 **자기 글을 자기가 승인하는 절차**가 됐다.

`author varchar(50)` 열에 `-- 노출은 마스킹된 형태로` 라고 적혀 있는 것도
같은 전제의 흔적이다. 마스킹할 작성자가 애초에 없다.

## 레퍼런스는 어떻게 하는가

| | 작성 주체 | 방식 |
|---|---|---|
| 탐나넷 | 로그인 회원 | `free_write.php` 가 로그인 게이트. 비회원 글도 `비회원` 으로 섞여 있다 |
| 인터넷다모아 | **익명 방문자** | 작성자 입력란이 아예 없다(전부 `익명`). 제목·비밀번호·이미지1·내용만. 비밀번호는 **수정용** |

둘 다 **방문자가 직접 쓴다.** 다모아는 계정 없이 쓰게 하고, 수정 권한만
비밀번호로 묶는다. 작성자 이름을 아예 받지 않는 선택이 눈에 띈다 —
받지 않으면 마스킹할 것도, 유출될 것도 없다.

## 선택지

### A. 방문자 작성 경로를 만든다 (권장)

- `reviews` 에 anon INSERT 정책 + `is_published = false` 강제
- `/api/reviews` 라우트 — Turnstile·zod·레이트리밋을 `/api/leads` 와 같은 자리에서
- `/review` 에 작성 폼
- 어드민에 승인 화면

**작성자 이름을 받지 않는다.** 다모아와 같은 선택이다. 이유는 개인정보를
한 종류라도 덜 받는 쪽이 항상 안전하고, 후기의 신뢰는 이름이 아니라
"실제 가입자가 썼다" 는 경로에서 나오기 때문이다. `author` 열은 비워 둔다.
(수정·삭제용 비밀번호도 받지 않는다 — 비밀번호를 받으면 그걸 보관·검증해야
하고, 재사용 비밀번호가 들어오면 그 자체가 유출 리스크다. 수정이 필요하면
운영자에게 요청하는 쪽이 받는 정보가 더 적다.)

### B. 후기 게시판을 "운영자 작성" 으로 명시한다

글마다 "운영자 작성" 을 표기하고 섹션 이름을 후기가 아닌 것으로 바꾼다.
법적 리스크는 줄지만 **후기 게시판이 아니게 된다** — 레퍼런스 두 곳이 모두
후기를 두는 이유(전환에 직접 기여)가 사라진다.

### C. 아무것도 안 한다

가장 위험하다. 운영자가 선의로 "이런 식으로 쓰면 되겠지" 하고 샘플 후기를
넣는 순간 위반이 된다. 구조가 그걸 **권하고 있다** — 읽는 화면은 있는데
쓰는 사람이 운영자뿐이다.

## 결정

**A** 로 간다. 근거는 두 가지다.
1. 스키마가 이미 A 를 전제로 설계돼 있다(`is_published default false`,
   `-- 승인 후 노출`). 빠진 조각을 채우는 쪽이 설계와 일치한다.
2. CLAUDE.md 규칙 1 의 보호 대상 안쪽이다. 규칙이 `leads` 만 이름으로
   적었다는 이유로 비켜 가는 건 규칙을 글자로만 읽는 것이다.

구현 중에도 **승인 전 글은 절대 공개되지 않아야** 한다. 그 보장은 애플리케이션
코드가 아니라 RLS 에 둔다 — anon 의 INSERT 는 `is_published = false` 인 행만
통과시키고, UPDATE 는 아예 주지 않는다. 그러면 제출자가 나중에 자기 글을
게시 상태로 바꿀 경로가 없다.
